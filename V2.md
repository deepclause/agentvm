# AgentVM 0.2.0 — Design & Plan

> This file is the working plan for the `0.2.0` release. The goal is a single,
> reviewable, large pull request against `deepclause/agentvm`.

## 1. Goals

1. **Portable runtime.** Pure Node ≥ 20, built-in modules only. No npm runtime
   dependencies, no native binaries, no Go `c2w-net`, no Wasmtime at runtime.
2. **Stable networking.** Correct multi-connection TCP/UDP NAT, DNS through the
   host resolver (no hardcoded `8.8.8.8`), ICMP echo, connection aborts and
   large transfers handled cleanly.
3. **Faster.** Keep the warm persistent VM (already ~1.07 s cold boot, ~10 ms
   warm `exec`). Reduce host-side overhead and fix pathological TCP state
   cleanup.
4. **Better agent UX.** Keep the `AgentVM` API, add streaming `spawn()`, a
   JSON-RPC `serve` mode, and a more capable CLI.
5. **Backward compatible.** Existing `AgentVM` callers keep working.

## 2. What is wrong today (root causes)

The VM is one NIC over one emulator socket (`-net socket`, fd 3 → accept → fd 4).
That socket carries **QEMU-framed Ethernet frames**, not a TCP stream. All guest
TCP connections are multiplexed inside those frames.

The current code treats that frame pipe as if it were a single TCP connection:

- `sock_recv()` returns **EOF for the whole NIC** whenever *any* TCP session is
  in `FIN_WAIT`/`CLOSED_BY_REMOTE` (`hasReceivedFin()` is global).
- That EOF then calls `closeSocket()`, which closes **one arbitrary** session and
  resets `netConnectionAccepted`/`sockRecvBuffer`.
- Result: the first finished connection poisons later ones ("DNS fails after
  first download").
- `closeSocket()` only closes one session and then `break`s.
- The TCP state machine has no retransmission, no window handling, and partial
  `seq/ack` bookkeeping.

## 3. Architecture change (networking)

Introduce a clean split:

- **Frame pipe (fd 3/4):** always alive, always a byte stream of
  `uint32 length + Ethernet frame`. `sock_recv` returns `EAGAIN` when empty and
  never synthesizes per-connection EOF.
- **Gateway (`NetworkStack`):** terminates IP/TCP/UDP per flow. A TCP flow is a
  proxy: guest-facing TCP endpoint (JS, correct seq/ack/window/retransmit) ⇄
  host `net.Socket` (Node does host TCP).

`NetworkStack` becomes a proper flow table:

```
natTable: Map<"TCP:srcIp:srcPort:dstIp:dstPort", TcpFlow>
udpTable: Map<"UDP:srcIp:srcPort:dstIp:dstPort", UdpFlow>
```

`TcpFlow` states: `SYN_SENT`, `ESTABLISHED`, `FIN_WAIT_1`, `FIN_WAIT_2`,
`CLOSE_WAIT`, `CLOSING`, `LAST_ACK`, `CLOSED`. Each flow owns its guest-facing
`seq`/`ack`, a small retransmission queue, and a host socket.

DNS is terminated on the gateway: guest UDP:53 → main-thread `dns.promises`
lookup → single UDP reply. DHCP advertises the gateway IP as DNS.

## 4. Workstreams

- **A. Networking rewrite** — `src/network.js` + the socket layer in
  `src/worker.js`. Drop-in `NetworkStack` public surface where possible.
- **B. Runtime ergonomics** — extract the `node:wasi` monkey-patches into
  `src/wasi-shim.js`; add `spawn()` streaming; clean up debug noise; expose
  `snapshot`/`info`.
- **C. CLI + bridge** — `bin/cli.js` gains `serve` (JSON-RPC over HTTP) and
  `doctor`; keep `run`/`shell` behavior.
- **D. SDK/tools** — Vercel AI SDK `tool()` definition, `agentvm` compat shim,
  Python client example.
- **E. Tests + docs** — unit tests for the new TCP proxy, integration matrix
  (DNS, concurrent, abort, large transfer), README/DESIGN updates, version bump
  to `0.2.0`.

## 5. Test matrix (networking)

Local HTTP server on the host (port on `192.168.127.1`), exercised from the
guest with busybox `wget` (and `curl`/`python3` when the image has them):

1. DNS via host resolver (external hostname).
2. Sequential downloads (the historical bug).
3. Concurrent downloads (two `wget &`).
4. 1 MB / 10 MB transfer integrity (checksum).
5. Connection abort (`curl` killed mid-transfer), then a fresh download.
6. UDP (DNS) while a TCP download is active.
7. Idle flow reaping (no fd/state leak after many requests).

## 6. Ultimate acceptance test

The 0.2 release gate is an end-to-end agent workload, not just unit tests:

> Boot a riscv64 Alpine image that has **Python and Node.js/npm installed**,
> then inside the VM:
>
> 1. `pip install <package>` (downloads + builds wheels over HTTPS).
> 2. `npm install <package>` (many small concurrent HTTPS downloads).
> 3. **Install the `pi` coding agent and run it** against a trivial task.

This exercises DNS, HTTPS/TLS, pip/npm (multiple concurrent keep-alive and
non-keep-alive connections), large and small transfers, connection reuse, and a
long-running interactive process — everything an agent VM must do in production.

The acceptance image is built with container2wasm (build-time tool) from the
Dockerfile in `image/`:

```bash
# build-time only; the shipped artifact is a plain .wasm + manifest.json
cd image && ./build.sh
```

This image is not a runtime dependency; the runtime remains pure Node.

## 7. Deliverable shape

- `package.json` version `0.2.0`, no `dependencies` (dev-only deps stay).
- `src/{index,worker,network,ringbuffer,wasi-shim}.js`.
- `bin/cli.js` with `run | shell | serve | doctor`.
- `example/` updated agent/tool examples.
- `test/` unit + integration tests.
